# Semantic models
id: fabric-m07-semantic-models
track: fabric
verified: 2026-10

## What we're learning
A **semantic model** (formerly a Power BI dataset) is the business layer between data and reports. It holds tables, **relationships**, **DAX measures** (Revenue, Margin %, Year-to-date sales), hierarchies, formatting, and **row-level and object-level security**. Reports, Excel, Copilot and data agents query the model, not the raw tables.

A model's tables use a **storage mode**:
- **Import**: data is copied into the in-memory VertiPaq engine on refresh. Fastest queries, but refresh time and memory limits apply.
- **DirectQuery**: every visual sends a query to the source. Fresh, but slower and puts load on the source.
- **Direct Lake**: reads Delta tables from OneLake straight into VertiPaq, without a copy refresh.
- **Composite** models mix modes.

## Benefit
Defining a measure once in a model means every report shows the same number. A clean **star schema** (fact tables joined to dimension tables) is what makes models fast and DAX simple.

## Limits and misconceptions
- A semantic model is not a data warehouse. Heavy transformation belongs upstream; models should receive clean, star-shaped tables.
- Model RLS protects only queries through the model. Users with direct access to the lakehouse or warehouse are not filtered by it.
- Lakehouses and warehouses no longer get an automatic default semantic model; models are created deliberately.

## Remember this
The semantic model is where business definitions and report security live; feed it a clean star schema.

# Direct Lake
id: fabric-m07-direct-lake
track: fabric
verified: 2026-10

## What we're learning
**Direct Lake** is a semantic model storage mode that loads columns from **Delta tables in OneLake** directly into the VertiPaq engine when queries need them. There is no import copy to refresh. Instead, a lightweight **framing** step points the model at the latest Delta version, which takes seconds.

There are two flavours (October 2026):
- **Direct Lake on OneLake**: can use tables from several Fabric items and be combined with import tables. It respects **OneLake security**. It never falls back to DirectQuery; if limits are exceeded, the refresh fails. Microsoft recommends it for new models (its GA status was not explicitly confirmed in the docs checked).
- **Direct Lake on SQL endpoints**: uses one item's SQL analytics endpoint. It **falls back to DirectQuery** (slower) when it meets SQL views, SQL row-level security, or tables beyond its guardrails. A setting can force errors instead of silent fallback.

**Guardrails** depend on the capacity size: maximum Parquet files, row groups and rows per table, and memory per model. Small SKUs have tight limits.

## Benefit
Import-like query speed on large data that is always as fresh as the last Delta commit, without scheduling long refreshes or storing a second copy.

## Limits and misconceptions
- Performance depends on table layout. V-Order, compaction and sensible row-group sizes matter.
- The first query after framing can be slower while columns load ("transcoding").
- Direct Lake cannot use a gateway, does not work in My workspace, and needs a Fabric F capacity.
- Silent DirectQuery fallback on the SQL flavour is a common surprise; check whether queries are falling back before blaming DAX.

## Remember this
Direct Lake reads OneLake Delta tables straight into Power BI's engine; keep tables compact and watch for fallback.

# Reports, dashboards and apps
id: fabric-m07-reports
track: fabric
verified: 2026-10

## What we're learning
Fabric includes the full Power BI service:

- **Reports**: interactive pages of visuals on a semantic model, built in Power BI Desktop or the browser.
- **Dashboards**: single-page tiles pinned from reports; a legacy concept that is still supported.
- **Paginated reports**: pixel-perfect, printable reports built with Power BI Report Builder, for invoices, statements and regulatory output. They can read semantic models or sources directly through gateways.
- **Apps**: the way to distribute content to large audiences. **Workspace apps** (one per workspace, versioned) were the classic form; **org apps** are a newer GA item type that allow several apps per workspace, with audiences, and can include notebooks and real-time dashboards as well as reports.

## Benefit
Report authors stay inside the same governed platform as the data, so lineage, sensitivity labels and endorsement flow from lakehouse to report.

## Limits and misconceptions
- Licensing still decides who can view: on capacities smaller than F64, every viewer needs a Pro or PPU licence.
- Report-level filters are not security. Use RLS in the model.
- Export to Excel or CSV takes data outside Fabric's controls; sensitivity labels protect some export paths, not all.

## Remember this
Reports explore, paginated reports print, and apps distribute; security belongs in the model, not the report.
